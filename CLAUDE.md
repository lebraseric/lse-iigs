# CLAUDE.md — Implémentation physique du L.S.E. sur Apple IIGS / ORCA-C

Ce fichier reprend les instructions du projet « LSE-IIGS » (claude.ai) pour qu'elles s'appliquent aussi dans VS Code. Il est volontairement condensé : le texte intégral du « Conditionnement » reste la référence (`05-IMPLEMENTATION/contraintes/Conditionnement.md`).

Langue de travail : **français** (documents, décisions IMP, commentaires de code, messages de commit).

## Mission

Réaliser physiquement la machine L.S.E. déjà définie par les documents normatifs. **Ne pas reconcevoir le L.S.E.**

- Plateforme : Apple IIGS, 65816, 4 Mio RAM, disque 32 Mio, lancement depuis le shell ORCA.
- Application **exclusivement textuelle**, sans Toolbox graphique.
- Langage : C. Compilateur : **ORCA/C 2.2.1**. La compatibilité réelle avec ORCA/C 2.2.1 prime sur le standard C : ne jamais supposer une fonctionnalité C moderne sans l'avoir vérifiée dans `04-ORCA-C/` (manuel, `cc.notes.txt`).
- Dépendances système isolées derrière une couche d'adaptation (`src/plateforme/`) ; le noyau (`src/noyau/`) reste indépendant du terminal, du système de fichiers, du shell et du compilateur.

## Hiérarchie normative (impérative)

1. Conventions éditoriales + Catalogue des exigences (EXI-0001 à EXI-0062) — `01-NORMATIF/Referentiel-normatif-LSE.md`
2. Tomes I-II (architecture historique, machine abstraite)
3. Tome III (machine virtuelle, composants, responsabilités)
4. Tome IV (interfaces, formats, algorithmes, invariants)
5. Corpus historique (INRDP 1975, LSE15 1978, Noyelle) : sert à vérifier, jamais à contredire silencieusement les tomes
6. Documentation Apple IIGS / ORCA : répond uniquement à « comment réaliser physiquement ce qui est déjà spécifié ? »

Une décision d'implémentation ne peut modifier ni une propriété historique, ni une EXI, ni un mécanisme du Tome II, ni une responsabilité du Tome III, ni un contrat/invariant du Tome IV. Une limitation d'ORCA/C ne justifie jamais de modifier la spécification : chercher une autre réalisation, isoler l'adaptation, documenter, vérifier que le comportement L.S.E. est inchangé.

## Ordre de priorité des choix

Fidélité historique › EXI › Tome II › Tome III › Tome IV › simplicité › économie mémoire/stockage › compatibilité ORCA/C › maintenance. Aucune technique moderne introduite par simple confort.

## Résolution des ambiguïtés

Tome IV → Tome III → Tome II → Tome I + corpus historique → doc Apple IIGS/ORCA → **choix d'implémentation documenté (IMP-*) avant d'être codé**. Ne jamais modifier silencieusement la spécification.

## Interdictions

Interface graphique ; dépendance à la Toolbox ; imposer macOS/Windows/Unix ; bibliothèque moderne indisponible sur la cible ; supposer une mémoire abondante ; remplacer les fichiers L.S.E. par une base de données ; remplacer la représentation compilée par un langage intermédiaire moderne ; remplacer l'interpréteur par une VM générique ; supprimer une fonctionnalité historique « parce qu'elle paraît inutile » ; réinterpréter les commandes selon une syntaxe moderne ; modifier une EXI pour simplifier le code ; utiliser les pointeurs C comme modèle architectural (préférer identifiants/références internes : `HandleObjet`, index de symbole, numéro de ligne).

## Conservation historique obligatoire

Langage de commande français ; fonctionnement conversationnel ; structure par lignes ; compilation ligne par ligne (EXI-0001) ; représentation compilée exécutée par l'interpréteur ; décompilation ; commandes historiques ; gestion des programmes et des fichiers-données (identité + portée, temporaire/permanent, enregistrements, GARER/CHARGER/SUPPRIMER/CATALOGUER/ENCODER/DECODER) ; procédures/fonctions ; mécanismes d'erreur ; distinction fichier / tâche / état d'exécution (SWAP IN/OUT ne sont pas de simples rangements de fichiers-programmes).

Chaîne : programme source → représentation compilée → programme courant → fichier-programme.

## Décisions d'implémentation `IMP-*`

Tout choix non imposé par les tomes est enregistré dans `05-IMPLEMENTATION/decisions/` avec le format de `IMP-TEMPLATE.md` : identifiant, sujet, choix, alternatives envisagées, justification, impact mémoire, impact disque, impact performances, impact historique, références normatives, statut. Ne pas confondre avec les décisions `DEC` de la reconstruction documentaire.

**Numérotation : ne jamais réutiliser un identifiant.** Dernier identifiant attribué : `IMP-0282` (Bibliothécaire et fichiers §7 sexies). IMP-0147 appartient à la plage d'État d'exécution mais est rédigée dans le chapitre Compilateur. Vérifier `05-IMPLEMENTATION/decisions/REGISTRE.md` avant d'en créer un.

## Traçabilité

`HIS → EXI → VM → IV → IMP → CODE` (sans maillon historique : `EXI → VM → IV → IMP → CODE`). Chaque module important porte en en-tête : EXI satisfaites, VM réalisées, interfaces IV utilisées, décisions IMP appliquées, tests associés. Maintenir la matrice dans `05-IMPLEMENTATION/matrice-tracabilite/` dans les deux sens.

## Discipline de développement

Ordre amendé le 2026-10-22 (Conditionnement §17, arbitrage d'Éric) : représentation des objets → gestion mémoire → programme courant (minimal ou bouchon) → compilation → décompilation → pile d'évaluation et état d'exécution → interpréteur → dialogue → fichiers → procédures/fonctions → mécanismes complémentaires. RCI-M étant spécifiée et auditée avant le code, le compilateur ne définit pas la représentation. Chaque étape produit un système exécutable et testable. Priorité de la v1 : fiabilité, conformité fonctionnelle, faible mémoire, simplicité, traçabilité, débogage sur cible ; optimisations prématurées secondaires.

## Tests

Niveaux : représentation, composants, interfaces IV (normal / précondition invalide / erreur / limite / invariant), conformité EXI, historiques (exemples des manuels), sur cible (IIGS réel ou émulateur). Comparer à la spécification, jamais à une implémentation moderne.
